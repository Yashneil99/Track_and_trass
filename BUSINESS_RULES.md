# Business Rules: HUL Tea Bag Track N Trace

Status: DRAFT. Rules marked **Agreed** were confirmed in discussion. Rules marked **Proposed** await confirmation.
Never put secrets, passwords or tokens in this file.

## 1. Terms

| Term | Meaning |
|---|---|
| STN | Stock Transfer Note: the Excel/PDF listing what is on a truck (garden, grade, invoice, bags, weights). |
| Lot | One garden invoice on an STN (garden + invoice number). One lot can span several STN rows. |
| Slot | One expected bag inside a lot, created at STN upload with its expected weight. |
| Bag | A physical bag. Has a system-owned `bag_id`. |
| Tag | A reusable RFID tag. The tag number is factory-set and is read, never generated. |
| Bin | A storage location with a capacity (bags). |
| Process | A production process HUL defines (name, input and output material types). A separate master list, not a bag history. |

## 2. Bag identity (Agreed)

1. **The system owns the bag identity.** `bag_id` is generated by the system. The RFID tag number is not the bag's identity.
2. **STN upload creates the slots.** Each bag on the STN becomes a bag record with status `EXPECTED`, carrying its lot and expected weight. Example: a lot of 19 bags at 30 kg plus 1 bag at 21.4 kg makes 20 slots.
3. **Lots are per invoice.** A garden with several invoices on one truck has several lots.
4. **Receiving flow (when the truck arrives):**
   1. The operator scans the garden name **printed** on the bag. OCR runs in the handheld app and sends the garden name to the server.
   2. The server matches the name to a garden and proposes the matching open lots.
   3. The operator confirms the lot.
   4. The operator attaches an RFID tag to the bag and scans it.
   5. The server checks the tag is **available for use** (status `AVAILABLE`). If it is `IN_USE`, `LOST` or `DAMAGED`, the scan is rejected.
   6. The server links the tag to one free `EXPECTED` slot of that lot, and the bag becomes `IN_TRANSIT`.
5. **OCR is a search, not an identity.** The operator always confirms. The raw OCR text is stored on the bag event for audit.
6. **A tag scan is blocked until a lot is confirmed.**
7. **Gardens are created automatically at STN upload (Agreed).** No approval step. If the garden name is not found, it is inserted. If it is found, the stored garden is used. Admins merge duplicates later on a side-by-side screen. Lookup checks `gardens.name` first, then `garden_aliases`.
8. **At the OCR scan, an unknown garden name does not create a garden (Proposed, decision pending).** Every garden on a real STN already exists, so a name that matches nothing is an OCR misread or a bag not on any STN. Creating a garden from raw OCR text would add junk gardens and a bag with no lot. Instead the bag is flagged as an *unexpected bag* and the admin gets a live alert. You asked for insert-if-missing here too: if you still want that, the bag would be created without a lot.
9. **Exceptions:**
   - No free slot left in the lot: an *extra bag*, flagged and not linked.
   - OCR matches no open lot: an *unexpected bag*, flagged.
   - Slots still `EXPECTED` when an admin closes the lot are the *missing bags* (Proposed).
10. **Lot QR is an optional fallback** if OCR fails (Proposed).
11. **A tag the system has never seen** is registered automatically as `AVAILABLE` on its first scan (Agreed).

## 3. Bag lifecycle (Agreed, names to confirm)

```
EXPECTED ─► IN_TRANSIT ─► STORED ─► DISPATCHED_TO_PRODUCTION ─► DELIVERED
   (STN)     (tag scanned   (reached    (picked for a request,     (scanned at
              at the truck)  its bin)    scanned out)               production)

DAMAGED: can be set on a bag at any step before DELIVERED.
Expired is a flag from the expiry date, not a status.
```

| Status | When it is set | By |
|---|---|---|
| `EXPECTED` | STN upload creates the slot | system |
| `IN_TRANSIT` | Tag attached and scanned at the truck | operator |
| `STORED` | Bag scanned into its bin ("reached its location") | operator |
| `DISPATCHED_TO_PRODUCTION` | A request was raised and the bag is picked and scanned out | operator |
| `DELIVERED` | The bag is put into the process and scanned at production | production person |
| `DAMAGED` | The bag is found damaged | operator |

Effects of each step:
- `STORED`: the bag counts in the bin's occupied number (reserved goes down by one).
- `DISPATCHED_TO_PRODUCTION`: the bag leaves its bin, so occupied goes down by one. The tag stays on the bag so production can scan it.
- `DELIVERED`: the tag is released and becomes `AVAILABLE`.
- `DAMAGED`: the tag is released and becomes `AVAILABLE`, the bin's occupied goes down if it was stored, and the admin sees the damaged bag with its garden.

## 4. Lot progress (Agreed)

1. A lot has counters: `bags_expected`, `bags_tagged` (tag scanned so far), `bags_stored` (reached their bins), `bags_damaged`. `bags_stored` counts bags that have reached a bin and never goes down. `bags_damaged` counts only bags damaged *before* reaching a bin; a bag damaged after it was stored is still counted as stored.
2. The lot status is set **automatically** from the counters:

| Lot status | When |
|---|---|
| `EXPECTED` | No bag tagged yet |
| `IN_TRANSIT` | Some bags tagged, none stored yet |
| `PARTIALLY_STORED` | At least one bag stored, but not all |
| `STORED` | `bags_stored + bags_damaged = bags_expected` |

Example: a lot of 20 where 10 bags have reached their bins shows `bags_stored = 10` and status `PARTIALLY_STORED` until the other 10 arrive.

3. The counters change only inside the same transaction as the bag event, and a nightly job recounts them from the bags (Proposed).

## 5. RFID tag lifecycle (Agreed: tags are reusable)

1. A tag has one state: `AVAILABLE` (free to use) or `IN_USE` (linked to a bag). `LOST` and `DAMAGED` are extra states (Proposed).
2. A tag can have **only one active bag at a time**.
3. Linking a tag to a bag sets it `IN_USE` and writes an assignment record (tag, bag, assigned_at). A tag must be `AVAILABLE` to be linked.
4. **The tag is released automatically when the bag is `DELIVERED` or `DAMAGED`**: `released_at` is set and the tag becomes `AVAILABLE`.
5. Assignment history is never deleted. One tag will have many bags over time, one after another.
6. A scan always means "the bag this tag is linked to right now". History is found by date.
7. Scanning a tag that has no active bag, when the system expects one, is rejected and alerts the admin.
8. A physical process for recovering tags (who removes them, where they go back) must be defined by HUL. Open question.

## 6. Splitting a lot across bins and bin numbers

1. **One table for all allocations** (Proposed), with one row per (lot, bin, bag count). No separate "split" table and no `allocated_location` column on the lot.
2. A lot that fits in one bin has one row. A lot that does not fit has several rows. The code path is the same for both.
3. The sum of the rows for a lot must equal the lot's bag count.
4. Reservation of a bin is the sum of allocated-but-not-yet-placed bags from these rows. It is kept in a single counter that changes in one place (see `DATA_MODELING.md`), not edited by hand in many places.
5. A bag placed in a bin reduces that bin's reservation by one and raises its occupancy by one. If a bag's bin changes, the old bin is released and the new one is taken.
6. **Every bin shows three numbers (Agreed):** total capacity, reserved, and available.
   - Occupied = bags physically in the bin.
   - Reserved = bags promised to the bin by a lot allocation but not yet placed.
   - Available = capacity - occupied - reserved.
7. A bin can never be over-booked: occupied + reserved must not exceed capacity. The database enforces this (Proposed).
8. **Capacity changes only when an admin changes it (Agreed).** Reserving, placing, moving or dispatching bags never changes capacity. They change only occupied, reserved and available.
9. A capacity decrease is rejected if the new capacity is lower than occupied + reserved (Proposed).
10. Every capacity change is recorded: old value, new value, who, when, and a reason (Proposed). Available is recalculated automatically.

## 7. Expiry (Agreed: default one year, changed by admin)

1. Every bag has its own `expiry_date`.
2. The default is **one year** from the STN data (Agreed), and it is **set when the STN is uploaded**, together with the bag records. The start date is the STN date in the file (fallback: the upload date if the file has none). The one-year period is a setting, not hard-coded.
3. **Only an admin can change a bag's expiry date** (Agreed).
4. Every edit is recorded in the bag's event history: old date, new date, who, when and a required reason (Proposed).
5. An admin can edit one bag or a whole lot (Proposed). A lot edit writes one event per bag.
6. Picking for outward uses **first-expiry-first-out**: the bag that expires soonest is picked first (Proposed).
7. Expired bags are flagged and cannot be dispatched to production without an admin override (Proposed).
8. Bags nearing expiry (a configurable number of days) appear in the admin alert list (Proposed).

## 8. Outward to production (Agreed)

1. A request is raised for bags (garden, grade, number of bags).
2. The operator picks the bags and scans each one out: the bag becomes `DISPATCHED_TO_PRODUCTION`.
3. The request becomes `COMPLETED` when every requested bag has been scanned out.
4. At production, the person who puts a bag into a process scans it: the bag becomes `DELIVERED` and its tag is released.
5. The delivery scan can record which **process** the bag went into (Proposed; links to the process master list).
6. Only one `PENDING` request is allowed per location at a time (kept from the current system).

## 9. Roles (Agreed: the admin does the managing work)

| Role | Can do |
|---|---|
| Admin | Edit expiry, change bin capacity, merge gardens, override an expired bag, close a lot, manage users, define processes, see damaged bags, receive live alerts |
| Operator | Scan at the truck (OCR + tag), put bags in bins, scan bags out for a request, mark a bag damaged |
| Production person | Scan a bag as delivered into a process (the exact role name is to be confirmed) |

## 10. Live alerts to the admin (Agreed that admin needs live alerts; the list is Proposed)

- A bag is marked damaged (with its garden).
- An extra bag or an unexpected bag is scanned.
- A rejected tag scan (tag in use, lost, damaged, or no active bag).
- A lot is closed with missing bags.
- Bags are expired or near expiry.

Alerts are pushed live over WebSocket to admins only, and also saved so an admin who was offline sees them later.
